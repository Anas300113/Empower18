# Empower18 Reference Repository Assessment

**Scope.** This report assesses seven reference repositories against Empower18’s current React 19/Vite, Wouter, TanStack Query, tRPC 11, Express, Drizzle/PostgreSQL, Supabase Auth, TypeScript/Vitest architecture. It is a technical adoption assessment, not an implementation plan. No code, dependency, migration, or database changes were made.

## Executive assessment

The repositories are most valuable as **bounded patterns**, not as drop-in platforms. Empower18 should preserve its existing identity, authorization, API, persistence, and participant UX boundaries. The strongest near-term opportunities are: (1) finish a real opportunity ingestion/review vertical slice informed by career-ops and JobSpy; (2) define a structured CV/document model informed by JSON Resume and Reactive Resume; and (3) add TanStack Table only for a proven data-heavy/admin workflow. Refine is conditional and should be limited to a separate admin/content-reviewer console. The Supabase React user-management example is useful only for small UI patterns such as account/avatar separation and auth lifecycle cleanup.

## Prioritized roadmap

### P0 — Protect the existing architecture and establish real domain contracts

1. **Keep one security and data boundary.** Continue using Supabase Auth token verification, server-fetched roles, tRPC middleware, Drizzle repositories/transactions, and RLS. Do not introduce direct browser CRUD through a reference repository’s Supabase, Prisma, Better Auth, oRPC, or file-based paths. The relevant Empower18 boundaries are `server/_core/context.ts`, `server/_core/trpc.ts`, `server/_core/supabase.ts`, `server/routers.ts`, `server/db/`, `drizzle/schema.ts`, and `drizzle/migrations/` [1][2][3].
2. **Replace prototype assumptions with typed server contracts.** The current opportunity router is empty and the visible platform still uses sample/static data and local state. Prioritize protected opportunity list/detail, saved-opportunity, application, and notification procedures before adopting UI frameworks [4][5].
3. **Define authoritative lifecycle and authorization rules.** Centralize allowed opportunity publication/verification transitions and application-stage transitions. Every mutation must enforce identity, role, ownership, legal transitions, and audit/event behavior server-side; UI checks are advisory only.
4. **Establish ingestion policy before scraping.** For every source, record permission/terms, retrieval schedule, rate limit, authority, health, provenance, and retention. Prefer official APIs, RSS/JSON feeds, or licensed aggregators. Do not treat an MIT scraper license as permission to republish third-party content [6][7].
5. **Protect youth-user data.** Treat CVs, accessibility needs, age bands, applications, notes, contacts, and AI prompts as sensitive. Define consent, retention/deletion, redaction, private storage, signed access, audit, and provider-disclosure requirements before public sharing or AI features.

### P1 — Build the first useful vertical slices

1. **Opportunity ingestion and review.** Implement one approved provider adapter behind a worker/service boundary. Normalize, deduplicate, record sync health and evidence, store as unpublished/pending review, and expose an admin review queue through tRPC. Adapt career-ops’ staged pipeline and evidence-confidence model, and JobSpy’s strict canonical DTO, partial-success diagnostics, and adapter registry [6][7].
2. **Structured CV model.** Add an Empower18-owned, versioned structured CV document associated with the existing Supabase UUID. Keep uploaded originals in the existing `resumes` model and do not conflate files with canonical editable content. Use JSON Resume as an interoperability contract and Reactive Resume as a model for version snapshots and immutable sent-document linkage [8][9].
3. **Application-time document snapshots.** When a resume/CV or letter is used for an application, retain the exact sent version. Keep application history append-only and auditable rather than allowing later document edits to rewrite history.
4. **Admin review grid.** If the first review queue needs dense sorting/filtering/pagination, pilot `@tanstack/react-table` with server-side query state and existing `client/src/components/ui/table.tsx`. Keep student discovery as accessible cards/lists [10].
5. **Read-only Refine spike, only if justified.** After domain routers stabilize, test a separate admin/content-reviewer surface over a custom tRPC Data Provider. Start with opportunity review read-only; add mutations only after authorization, cache, dates/numerics, and audit behavior are proven [11].

### P2 — Expand only after P0/P1 evidence

1. Add one accessible CV theme and preview/export path; defer broad theme ingestion, public registry publishing, AI/ATS scoring, and multi-format parity.
2. Add optional AI evaluation as a queued, consented, structured service with evidence, confidence, model metadata, quotas, retries, and human approval. Never use an LLM for hard eligibility, age, district, deadline, verification, or publication decisions [6].
3. Add public CV/profile links only after explicit consent, redaction, revocation, enumeration resistance, noindex defaults where appropriate, moderation, and retention controls.
4. Consider Refine only if repeated CRUD/table/form work across several admin resources outweighs the cost of a second abstraction. Otherwise use native typed tRPC/TanStack Query hooks and the existing UI.
5. Reassess any dependency or copied code at a pinned commit with lockfile/SBOM, accessibility, bundle, operational, and license review.

## Repository assessments

### 1. Refine

**What it is and source evidence.** Refine is an MIT-licensed, headless React meta-framework centered on resources and provider contracts. Its core package and workspace metadata are at the upstream root/package manifests [11]. Official documentation covers data, auth, access control, routing, notifications, audit logs, realtime, and UI integrations [12]. Data hooks include list/detail/create/update/delete/table/form/select/custom operations, and documented providers include REST, GraphQL, Supabase, Hasura, Strapi, and NestJS [12].

**Specific Empower18 adaptation.** Create a custom Data Provider backed by typed tRPC for one resource, preferably opportunity review. Map list/show/create/update/custom actions to explicit procedures while preserving superjson, pagination, filters, errors, and invalidation. Add explicit procedures for opportunity list/detail, draft/edit, submit-for-review, verify, publish/pause/close, source reliability, organisation links, and audit events before building the screen. Use Refine Access Control as a UI projection of server capabilities; obtain capabilities from a protected endpoint and never trust browser roles.

Use Refine’s table/form orchestration for admin filtering, sorting, pagination, validation feedback, and invalidation, but model publishing, verification, and application transitions as explicit custom actions rather than unrestricted generic updates. Keep the participant app and Wouter routes intact; use a separate admin shell/router or a carefully tested adapter.

**Avoid.** Do not replace the participant app, use the Supabase provider as a second production write path, expose service-role/direct DB credentials, or model sensitive documents and lifecycle transitions as generic CRUD. Refine does not provide tRPC 11, Drizzle repositories, Supabase JWT verification, RLS design, migrations, eligibility rules, source ingestion, AI safeguards, or application submission [11][12].

**Risks.** Mixing Refine hooks with existing tRPC hooks can create duplicate query keys and invalidation gaps. Generic resource semantics may flatten opportunity states, verification evidence, application history, and ownership. A second router can duplicate guards and navigation. Its CRUD orientation is a poor fit for youth-facing discovery, onboarding, careers, support, notifications, and accessibility-first experiences.

### 2. TanStack Table

**What it is and source evidence.** TanStack Table is a headless, framework-agnostic table engine. The current inspected React adapter is v9.3.1, with table-core exports for sorting, filtering, grouping, aggregation, pagination, pinning, sizing, visibility, expansion, faceting, and row/cell selection [10]. The official state guide documents controlled state slices, external atoms, query-key-driven server pagination, `manualPagination`, and `rowCount` [10].

**Specific Empower18 adaptation.** Start with an admin opportunity review queue. Define a validated DTO/state contract containing page index/size, allow-listed sort field/direction, search, district, type/route, verification/publication flags, and deadline range. Add a protected tRPC procedure that maps only allow-listed fields to Drizzle expressions, applies publication/role/ownership rules, returns rows plus total count, and uses appropriate indexes. Put normalized state in the TanStack Query key; debounce search and reset the page after filter changes.

Drive the existing semantic primitives in `client/src/components/ui/table.tsx`; do not replace cards in `client/src/pages/Platform.tsx` by default. Keep student discovery as a list/card UX and reserve dense tables for admins or power users. Add Vitest coverage for state serialization, query validation, sort mapping, permission failures, and empty/loading/error states.

**Avoid.** Do not accept arbitrary client column IDs or SQL-like expressions, download all rows for client filtering, duplicate state ownership across URL/React/atoms/Query, or copy v8 examples into a v9 implementation. Table does not provide auth, persistence, API transport, export, virtualization, or accessibility behavior.

**Risks.** Server-side grids require deterministic sort allow-lists, stable ordering, counts, indexes, and careful handling of dates, numerics, enums, nulls, and JSON. Selection is not authorization. Interactive cells, responsive alternatives, pinned columns, and virtualization increase keyboard and screen-reader testing burden.

### 3. Supabase React user-management example

**What it is and source evidence.** The upstream example is a small Vite React app with Supabase Auth, direct browser profile queries/upserts, and avatar Storage operations [13]. Current `App.jsx` uses `getClaims` and auth-state subscription cleanup, while the README contains an older `getUser` snippet; this source/README drift makes pinning a commit important [13]. Its SQL demonstrates profiles keyed by `auth.users.id`, RLS, and Storage policies, but includes public profile reads and permissive demo upload patterns [13].

**Specific Empower18 adaptation.** Reuse only the separation of Account and Avatar concerns, explicit loading/disabled states, auth subscription cleanup, and upsert-oriented profile UX. Implement these in existing TypeScript components using `client/src/_core/auth.ts`, `useAuth`, `server/routers/profile.ts`, and tRPC rather than direct `supabase.from` calls. If avatars become a requirement, design a user-scoped path such as `avatars/<auth-user-id>/<generated-file-id>`, validate type/size, persist only reviewed metadata/path, and use controlled access/signed URLs.

**Avoid.** Do not adopt public profile select policies, anyone-can-upload Storage policies, root-level random filenames, direct browser writes for protected domain data, Dashboard SQL as a second schema source, or `getSession` as server authorization. Do not add a second profile table: Empower18 already has profiles, student profiles, roles, onboarding, and RLS.

**Risks.** Direct writes bypass tRPC validation, cache invalidation, auditability, role checks, and transaction boundaries. Magic-link auth changes redirect, email, session, abuse-control, and UX requirements. Avatar support is not represented in the inspected Empower18 profile schema/router and would require a deliberate migration and policy review.

### 4. Reactive Resume

**What it is and source evidence.** Reactive Resume is an MIT-licensed, current v6-era monorepo with React/Vite web, Hono/Node server, oRPC, Better Auth, Drizzle/PostgreSQL, shared schema/domain packages, PDF/DOCX/ODT exporters, and application tracking [8]. Its resume model separates typed JSONB content from operational metadata, supports versions/trash/sharing/statistics, and its application model retains sent resume/letter versions [8].

**Specific Empower18 adaptation.** Add an Empower18-owned typed CV/document model and protected router under `server/routers/`, backed by Drizzle and existing Supabase UUID ownership/RLS. Start with one CV per student or a small library. Add document versions and an immutable sent-document snapshot/link to `studentApplications`. Adapt structured activity, contacts, follow-up notes, requirements, source URL, and tags only where compatible with Empower18’s `applicationStageEnum` and safeguarding policy. Implement export as a narrow adapter—initially JSON and a safe printable/PDF path—behind explicit tests and privacy boundaries.

Reuse UI concepts such as document library, version restore, list/board/calendar views, autosave feedback, and inline validation with Wouter, TanStack Query, tRPC, and existing Radix/Tailwind components. Keep pure document logic separate from browser/server export adapters if the feature grows.

**Avoid.** Do not clone the monorepo, replace Supabase Auth with Better Auth, copy Hono/oRPC middleware, import migrations wholesale, or adopt AI, scraping, MCP, Redis, passkeys, or broad exporters without a requirement and threat model. Do not copy template artwork, fonts, Pokémon-derived names/branding, or other assets without provenance/license review.

**Risks.** Auth identity mismatch can break RLS. JSONB/version/public-sharing migrations need explicit schema, retention, ownership, and RLS decisions. Public links create enumeration, password, rate-limit, consent, and safeguarding risks. High-quality PDF/DOCX output depends on substantial rendering and Unicode/test infrastructure; copying only UI would be fragile.

### 5. JSON Resume website/registry

**What it is and source evidence.** JSON Resume centers on a portable `resume.json` schema, validator, themes, and a registry. The analyzed registry is a Next.js/Prisma application with public username/GitHub-gist-oriented publishing, while the schema permits standard resume sections and extensible custom properties [9]. The core/theme package supports React 18/19 but uses its own style/token approach and styled-components [9].

**Specific Empower18 adaptation.** Use the JSON Resume schema as an interoperability boundary for a structured CV editor. Store a versioned document and metadata under the existing Supabase UUID, retaining uploaded originals separately in Empower18’s existing `resumes` model. Expose typed tRPC `get`, `upsert`, `validate`, `preview`, and `export` procedures. Validate at boundaries, return section-level errors, preserve unknown/custom fields, and keep safeguarding/matching data outside the public resume document. Start with one accessible, ATS-friendly theme and a private preview.

**Avoid.** Do not clone Next.js/Prisma/registry routes, add GitHub gist publication or a second auth system, make username URLs public by default, import dozens of themes, or add AI/vector/ATS infrastructure before the editor and consent model are useful. Sanitize free text/URLs and never render arbitrary HTML from imported resume data.

**Risks.** The public model conflicts with youth privacy and safeguarding. Schema evolution and permissive additional properties require a pinned schema version and migration policy. Themes may have individual licenses, CSS assumptions, accessibility gaps, or bundle costs. Public URLs and indexing need explicit consent, revocation, rate limits, and noindex policy.

### 6. career-ops

**What it is and source evidence.** career-ops is an MIT-licensed, local-first AI job-search system whose canonical workflow uses Markdown/files, prompt modes, Node scripts, optional Playwright, and an alpha loopback web UI [6]. Its valuable concepts are staged discovery, deterministic filtering, deduplication, liveness, confidence/evidence states, A–H evaluation, provenance, explicit tracker states, resumable work, and no-auto-submit safety [6]. Its employers registry is separately CC BY 4.0 and its brand is separately governed [6].

**Specific Empower18 adaptation.** Create a worker/service boundary for source fetch -> normalize -> deterministic age/location/title/eligibility filters -> URL/listing dedup -> liveness/verification -> admin review/publish. Persist each stage’s outcome in Empower18’s relational model. Adapt its normalized Job shape into `opportunitySources`/`opportunities`, and its lifecycle discipline into `applicationStageEnum` plus `applicationEvents`. Add queued, opt-in evaluation runs with model/provider metadata, evidence references, confidence, structured results, quotas, and explicit user approval. Store generated artifacts as versions; never overwrite authored CV/profile content implicitly.

**Avoid.** Do not use Markdown as a co-equal canonical store, dual-write without reconciliation, put prompt modes in the client, expose AI keys/browser automation, automatically scrape sources, use LLMs for hard eligibility/publication decisions, or add auto-apply/email/browser submission. Do not copy employers data without CC BY attribution and legal review.

**Risks.** The target assumes one local workspace, not multi-tenant identity or RLS. Hosted CV/AI data needs retention, consent, deletion, private storage, and provider disclosures. Long AI jobs need queues, retries, cancellation, quotas, and status records. Job-source terms and prompt-injection/untrusted-content risks remain application responsibilities.

### 7. JobSpy

**What it is and source evidence.** JobSpy is an MIT-licensed Python 3.10+ library/CLI that concurrently scrapes multiple job boards, validates inputs and `JobPost` records with Pydantic, returns pandas output, and exposes an optional process-local MCP preview/detail layer [7]. It has no React, TypeScript, Express, tRPC, PostgreSQL, authentication, or durable application state [7].

**Specific Empower18 adaptation.** Use it as an ingestion-pattern reference or isolated worker. Start with one legally approved source and one canonical upsert path. Map `site` to `opportunitySources`, source IDs to `sourceRecordId`, URLs to canonical/direct application URLs, title/description/location/type/salary/skills/posting date to approved opportunity fields, and company to controlled organisation matching. Record observed/last-seen times, raw hash or payload reference, parser version, sync run, warnings, errors, and stale/expired outcomes. Keep new rows unpublished/pending review.

Prefer official APIs, feeds, or licensed aggregators. If a Python worker is used, define a stable JSON contract and keep it outside the browser and request path. Add bounded concurrency, timeout/backoff/circuit breaking, per-source metrics, fixture tests, and a dead-letter/manual-review path.

**Avoid.** Do not vendor it into the frontend, scrape during user-facing tRPC requests, expose proxies/credentials, rely on its in-memory MCP cache, assume HTTP success means a valid listing, or publish every returned row. The README’s supported-board list does not establish permission to republish content, and it explicitly notes Google Jobs is unavailable [7].

**Risks.** Boards block or rate-limit requests; parsers change; descriptions can contain malicious markup or prompt injection; provider fields do not cover Empower18 age eligibility, district, verification, moderation, or application-window semantics. Repeated syncs need durable deduplication and conflict policy.

## Licensing and operational cautions

1. **MIT is not permission to ingest content.** Refine, TanStack Table, Reactive Resume, JSON Resume, career-ops, and JobSpy are reported as MIT-licensed; retain notices for copied code and review transitive package licenses [6][7][8][9][10][11]. MIT does not grant rights to scrape, store, display, or republish job-board descriptions, logos, employer data, or personal information.
2. **Apache-2.0 obligations apply to copied Supabase example code.** Preserve copyright/license and applicable NOTICE attribution, and mark modifications where required. Empower18’s MIT license does not erase Apache conditions [13].
3. **Separate asset and package review.** Reactive Resume templates/fonts/images and JSON Resume themes may have per-asset/per-package terms. Do not infer that every theme or asset inherits the repository’s top-level license.
4. **CC BY and trademark constraints.** career-ops’ employers registry is separately CC BY 4.0 and its brand/trademark policy is separate from code licensing [6]. Attribution and database-rights questions must be handled before reuse.
5. **Scraping and source terms.** Review Terms of Service, robots directives, API policies, database rights, privacy obligations, retention, and republishing permission source-by-source. Encode the decision in `opportunitySources` governance fields.
6. **Node/runtime compatibility.** The inspected Refine and TanStack package metadata requires Node >=20; Reactive Resume targets Node 24/pnpm 12, while Empower18’s deployed Node version must be verified before any dependency adoption [8][10][11].
7. **Operational isolation.** Scrapers, Playwright, PDF rendering, AI providers, and export tooling belong in server/worker boundaries, not the browser. Secrets, proxy credentials, service-role keys, and raw diagnostics must never reach client bundles.
8. **No migration or dependency assumption.** A reference repository’s dependency list is evidence of how it works, not a reason to add the dependency. Prefer existing Empower18 primitives and add only after a measured product need.

## Explicit unknowns and verification gates

Before adopting any item, verify the following in a pinned commit/version and the actual Empower18 deployment:

- Whether a maintained Refine tRPC 11 adapter exists; otherwise prototype the custom provider’s batching, superjson dates/numerics, errors, filters, pagination, invalidation, and Wouter coexistence.
- The exact TanStack Table major/API installed at adoption time; reconcile v9 docs with examples and verify React 19, Node, ESM, bundle, accessibility, and long-list behavior.
- The deployed Node/pnpm versions and lockfile/SBOM impact of every proposed package.
- Exact license and notices for selected JSON Resume/Reactive Resume themes, fonts, templates, icons, and transitive packages.
- Whether each opportunity source permits automated retrieval, retention, display, derivative normalization, and republishing in the intended geography and audience.
- How Supabase token refresh, `getClaims`/`getUser`, server verification, Storage signed URLs, RLS, and service-role separation behave in production; do not use `getSession` alone for server authorization.
- The final canonical CV representation: uploaded original, structured JSON, or both; schema versioning, partial onboarding, unknown-field round-tripping, and deletion/retention behavior.
- Public sharing requirements: consent, redaction, revocation, password/secret storage, enumeration resistance, noindex, moderation, and safeguarding review.
- Whether PDF/export tooling works in the deployment environment and preserves Unicode, layout, fonts, privacy, and accessible text; measure resource cost before adopting browser/server renderers.
- Queue/worker runtime, scheduler, retries, quotas, cancellation, dead-letter handling, and observability for ingestion and AI jobs.
- The exact semantics for Empower18 opportunity and application lifecycle transitions, including actor/source/reason, terminal states, audit records, and rollback/withdrawal rules.
- Cross-user isolation tests for profiles, CVs, applications, source records, AI evaluations, generated artifacts, and admin actions.
- Whether any upstream feature claims remain present and supported in the selected branch; do not infer behavior from README text when source and README diverge.
